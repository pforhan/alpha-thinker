# Implementation Plan: Alpha Thinker

This document tracks the specific engineering tasks required to move from design to a functional product.
Tasks should be sized to about one commit's worth of work.
As phases are completed they move from this file to the end of IMPLEMENTATION-PLAN-COMPLETED.md

## Phase 4: Advanced Features & Export

**Focus:** (1) Export, (2) Answer work. Other items are follow-ons/backlog within the phase.

### 4A. Export (primary)

#### 4A.1 Export model & rendering
- [x] **Export configuration model:** Define export options and an export artifact/record model (e.g. project id, created timestamp, filename, format, config snapshot, storage location/ref or status). Initial options should cover at least: output name (default derived in UI from project title), include/exclude ignored questions, unanswered items, drafts, answer revision history, and optional LLM-generated summaries/sections; keep the model extensible. — `model/Export.kt` adds `ExportConfig` (incl. `outputName`), `ExportFormat`, `ExportStatus`, and `ExportArtifact` (config snapshot + storage ref/status/error).
- [x] **Phase-structured Markdown renderer:** Generate a phase-grouped Markdown document (e.g. `## Scope & Goals`, `## Execution Plan`) with an opening "phase trail" summary (phases traversed, question counts, completion %). Rounds are internal metadata and do not appear in the export. Apply export options consistently (filtering/section inclusion). — `export/` adds a fluent `ExportDocument` sink (`MarkdownExportDocument` now, swappable for HTML later) and `ProjectExportRenderer` that groups by phase, builds the trail, and applies `ExportConfig` (incl. drafts/unanswered/ignored/revisions and optional per-phase summaries).
- [x] **Reconcile export with the transcript renderer:** Share the transcript’s *state semantics* and phase grouping (`PhaseTranscript`) with the export instead of maintaining a divergent format (`PlanningContext.kt` notes this intent, but `ProjectRepository.exportProject` currently predates phases, ignores rounds/`phaseForQuestion`, mishandles drafts/ignored questions, and emits malformed tables). Replace the current flat renderer and its single test as part of this work; export remains a detailed human document while the transcript remains the token-optimized prompt block. — `ProjectRepository.exportProject` now delegates to `ProjectExportRenderer` (default `ExportConfig`), the flat test is replaced with a phase-grouped/trail assertion, and `PlanningContext` KDoc points at the rebuilt export path.
- [x] **Optional summarization in export:** Decide and implement whether/how export reuses existing summarization/context-building logic for overview or per-phase summaries when requested by config. Run as async work with a clear fallback when no capable engine is available so export still succeeds without summaries. — `ProjectExportRenderer` consumes source-agnostic `phaseSummaries` when `ExportConfig.includeSummaries` is set; `export/ProjectExportSummarizer` reuses `PlanningContext` transcripts and `PlanningEngine.summarizePriorAnswers` for on-demand per-phase summaries (best-effort, returns none when the engine cannot summarize and omits failed phases) so export can still succeed and cached/background summaries can be supplied later.
- [x] **Unify programmatic summarization (refactor, step 1):** Introduce a shared, behavior-preserving summarization primitive/API (phase/transcript selection + summarize loop with strategy/hooks and a common result, e.g. phase summary text with optional coverage/metrics) so budget-driven compaction and best-effort export/background summarization share core logic. — `engine/core/PhaseSummarization.kt` introduced shared transcript selection and `summarizeOrNull` (reusing `PlanningContext`/`PlanningEngine.summarizePriorAnswers`), now evolved into `PhaseTranscript`/`compactionTranscripts`/`exportTranscripts`.
- [x] **Unify programmatic summarization (refactor, step 2):** Migrate `ProjectRepository.buildContext`/pre-generation compaction to the shared primitive while preserving exact semantics (candidate selection, oldest-first order, re-measure/stop-when-fits, `coversQuestionIds`/`asCompacted`, compaction logging/token deltas, final trim fallback). — `buildContext` now uses `PhaseSummarization.compactionTranscripts`/`summarize` in its budget-driven loop with identical control flow, logging, and results.
- [x] **Unify programmatic summarization (refactor, step 3):** Migrate `ProjectExportSummarizer` (and export’s on-demand path) to the shared primitive in best-effort per-phase mode (including export phase-selection rules such as current phase where appropriate), preserving fallback behavior. — `ProjectExportSummarizer` now uses `PhaseSummarization.exportTranscripts` + `summarizeOrNull` for best-effort per-phase summaries with the same fallback behavior.
- [x] **Unify programmatic summarization (cleanup):** Remove duplicated summarization logic, tighten names/types/docs, and align the shared result shape with future 4C background/persisted summaries and prompt/context reuse. — `ProjectRepository.checkContext` now uses `PhaseSummarization.compactionTranscripts` for consistency, `PhaseTranscript` provides `toSummarizedPhase(...)` for prompt/context/4C reuse, and minor cleanup/docs tightened. 
- [x] pull `PhaseTranscript`/`summarizablePhases` out of `PlanningContext` and remove delegation from `compactionCandidates`. — `PhaseTranscript` and `SummarizedPhase` are now top-level in `engine/core`; `PhaseSummarization` operates on `PhaseTranscript` (`compactionTranscripts`/`exportTranscripts`/`summarize*`) built from `PhaseQuestions`/`Project.allPhaseContent`, with rendering/token estimation via `PlanningContext`/`TokenEstimator`; `PlanningContext` no longer owns transcript/summary types or phase selection.

#### 4A.2 Generation, storage, and sharing
- [x] **Export generation service:** Add an app-level export/use-case flow that builds the document from project data, reports progress/state, integrates with task/activity logging as appropriate, and handles failures/cancellation without corrupting saved artifacts. — `repository/ExportRepository` creates a new artifact per `generateExport` (no `regenerate` API; UI can replay `ExportArtifact.config`), enqueues `TaskKind.Export`, and transitions `Pending`→`Generating`→`Completed/Failed` with task progress + activity-log notes, optional best-effort summaries, and no overwrite of completed artifacts on failure/cancellation.
- [x] **Local persistence strategy:** Decide where generated exports live (filesystem, DB table/blob, or metadata table + file) using a KMP-friendly approach. Implement saving, naming/collision handling, and retrieval of export records per project; define retention/overwrite/regenerate behavior. — file-backed, app-private managed exports (`export/ExportFileStore`, `PlatformContext.exportsDirectoryPath`, canonical artifact-id file refs) with Room metadata only (`ExportArtifactEntity`/DAO, `AppDatabase` v16, no DB content; config snapshot/status/error/canonical internal `storageRef`). File+DB are kept in sync as atomically as possible (write file then persist completed; failures surfaced/kept honest, missing completed files marked unavailable on read), deletes remove managed file + DB record (including project-delete cleanup), history is retained per project with display-name collision suffixing, and canonical refs always stay internal.
- [x] **Per-platform save/share (expect/actual):** Implement platform-specific save and share/open flows (e.g. Android share/save intent, desktop save dialog or open containing folder, web download) behind a common interface, with graceful degradation where a capability is unavailable. — `export/PlatformExportActions` is file-backed (`save/share/open` over internal path+content, canonical ref unchanged): Desktop supports save dialog copy and open/share via default handler, wasm uses download fallback, Android shares text/MIME intent (save/open degraded pending SAF/FileProvider/UI integration), iOS degrades gracefully pending picker/share-sheet UI integration. 4A.3 owns UI entry points/management.

#### 4A.4 Additional export formats (HTML / extensible)
- [x] **Canonical export snapshot model (versioned):** Define a serializable, versioned export snapshot/intermediate capturing export-relevant project state at a known revision (`Project.updatedAt` and/or a content fingerprint): header (id, title, synopsis, revision), ordered traversed phases and trail inputs (derived from `PhaseQuestions`/`allPhaseContent`/rounds), and rich per-phase question records in stable order (question id/text/timestamps/round-phase context as needed, ignored/compacted/draft state, committed answer + answeredAt, and answer revision history as available). Store canonical content so render-time `ExportConfig` filters (ignored/unanswered/drafts/revision history) and output format can be applied without re-reading live project state; "build once, render many formats". Document validity/invalidation: snapshot reusable while project revision unchanged even if render-only config/format/output name changes; project content changes (answers, drafts, questions, rounds/phases, revisions) invalidate the snapshot. — `export/ExportSnapshot.kt` adds versioned `@Serializable` `ExportSnapshot`/phase/question/answer records with `ExportSnapshot.from(Project)` (revision-keyed, canonical traversal/state incl. full answer history) and tests in `ExportSnapshotTest`.

Design for **multiple summary kinds** (there is only one engine-backed summarize method today): cache entries, provenance, and APIs must be intent-aware (e.g. compaction vs export/themes-insights), not assume a single summary per phase, and must accommodate future `PlanningEngine`/`PhaseSummarization` intent/mode changes without invalidating unrelated cached kinds. Define schema/versioning, read/write API, provenance (intent/model, covered content/revision), and invalidation when covered answers/drafts/questions/phases change or a phase is reopened; prefer cached summaries before on-demand generation (align with `SummarizedPhase` and `ProjectExportRenderer`/`ProjectExportSummarizer`’s `phaseSummaries` input). #### 4A.5 Portable project interchange (JSON, later)
Builds on the versioned canonical snapshot (4A.4) for machine-readable project transfer between Thinker instances; distinct from human-readable document exports (Markdown/HTML).

- [ ] **Interchange schema & envelope (versioned):** Define a portable, versioned JSON interchange format/envelope based on the canonical snapshot schema (or a compatible projection) plus interchange metadata (schema/app version, export timestamp, provenance as appropriate). Specify scope and compatibility guarantees: project core fields, rounds/phases, questions/answers, drafts/ignored state, answer revision history as applicable, and whether/how summaries/config/provenance are included. Define forward/backward compatibility and migration/validation rules for unknown or newer schema versions/fields.
- [ ] **Export to portable interchange:** Add a service/pipeline path to produce an interchange file from a valid project snapshot (+ selected metadata), with stable naming/extension and MIME type. Decide how it surfaces relative to document exports (separate action/format vs export library artifact), and route through per-platform save/share/open/download flows with clear capability degradation.
- [ ] **Import service & validation:** Implement parsing and validation (schema/version/migration, structural integrity of project/rounds/phases/questions/answers, id/reference consistency). Define import behavior: project identity and conflict handling (import as new project by default; consider replace/merge only if explicitly designed), id remapping/collision avoidance, and handling of missing/unknown/custom phases or fields. Content that cannot map to a known real phase must be represented as unassigned (`NoPhase`, 4C) rather than silently misattributed.
- [ ] **Import UI flow:** Provide entry point(s) and per-platform file selection/open to import an interchange file. Show a preview/validation summary before commit (project info, counts, warnings/errors, unknown-phase/unassigned items, and any conflict/identity choice), surface progress and actionable errors, and complete import into a browsable project state.
- [ ] **Unassigned-question slotting UX (post-import & general):** After import (and wherever unassigned/`NoPhase` questions arise), surface unassigned questions clearly and provide a UI/flow to slot them into real (built-in or custom) phases, individually or in bulk where appropriate. Integrate with phase-fit/reassignment suggestions when available (4C) while keeping manual choice/override primary, and ensure slotted results are reflected in project stats/timeline/export/summaries.

### 4C. Question pool & planning quality 
- [ ] **Global question pool:** Implement global question-pool management (create/edit questions reusable across projects) and integrate it with hardcoded/seed questions and LLM-generated questions (clarify precedence, dedupe, and per-project vs global scope). Define how pooled/user-defined questions are phased when added (assigned to a real phase vs unassigned/`NoPhase`; see unassigned-phase task) so they don’t silently misattribute to an arbitrary phase.
- [ ] **Unassigned phase (`NoPhase`) & slotting (design/model):** Consider a `NoPhase`/unassigned sentinel `Phase` implementation for questions without a real planning phase (e.g. portable import, global/user-defined questions, or cases where phase context is unknown). Define its semantics and touch points: stable key/identity and ordering/display rules (never a next-phase suggestion, not a visited library phase unless explicitly represented), `Phase` resolution/fromKey behavior, and how it appears (or is excluded) in `Project` phase lookup/stats/timeline, export snapshot/traversal/summaries, and prompt/context. Prefer explicit unassigned attribution over falling back to `ScopeGoals`; provide a path/UX to slot unassigned questions into real phases rather than leaving them orphaned.
- [ ] **Phase-fit reassignment & slotting (exploration/design spike):** Evaluate using a lightweight/decision model (e.g. a small local model such as tev1:0.8b, if viable) to rehome generated questions to a better-fitting phase when they don’t match the current phase, and/or to suggest target phases for unassigned (`NoPhase`) questions (e.g. after import or from the global pool). Capture feasibility, hosting/runtime constraints, confidence/override behavior, and when reassignment runs; implement only if justified. Always allow manual slotting into a real (built-in or custom) phase and treat suggestions as assistive, not authoritative.
- [ ] **Evaluate and expand summarize support:** Revisit summarization intent, prompts, and API shape (current single engine-backed method `PlanningEngine.summarizePriorAnswers` / `KoogPlanningEngine` prompt is compaction-oriented: “condense… so a later round does not ask again”; tests in `engine/KoogPlanningEngineTest.kt` focus on question generation and this compaction behavior). Plan for **multiple summary kinds/intents over time** (not just one method/prompt): prompt/context compaction vs export/document summaries vs cached/user-facing phase summaries may need different methods or an explicit intent/mode, prompts, and output expectations/length/structure (e.g. compaction favors settled decisions/constraints; export may favor themes, ideas, and insights). Update `PlanningEngine`/`PhaseSummarization`/`ProjectExportSummarizer` APIs, implementations, and tests accordingly, and ensure compaction, export, the 4A.4 snapshot+pipeline, and the persisted phase-summary cache can request, resolve, and store the appropriate kind per intent without conflating them.
- [ ] **Background phase summary generation (design/optional):** Build on the persisted phase-summary cache (4A.4) to optionally generate and store summaries when leaving a phase; if the phase is revisited, clear and regenerate on exit (or mark stale) per cache invalidation rules. Define when generation runs, user visibility/progress, and prompt/context usage, letting export and compaction prefer cached summaries before on-demand generation. Align generated summary intent with “Evaluate and expand summarize support” (compaction vs themes/insights) so reuse is correct.

## Phase 4.1: Research query synthesis (follows 4B answer work)

Improves the Research handoff by synthesizing project-aware search terms while preserving the question-generation JSON-array contract.

- [ ] **Query-synthesis engine API:** Add a `PlanningEngine` method to suggest **multiple ranked/labelled alternative query sets** for a question from project context (title, synopsis, phase, question, relevant prior answers/drafts). Engines that cannot synthesize (no capable model/window, Offline, etc.) must degrade gracefully to a cheap heuristic or title/question-derived terms—never fail the handoff.
- [ ] **Research dialog UX:** Present suggested query options as clickable actions (launch in browser and/or populate the question’s reference URL) alongside a free-form search-terms field. The user can always edit terms and launch immediately without waiting for suggestions.
- [ ] **On-demand synthesis + responsive UI:** When the answer dialog opens, kick off query generation if nothing is cached. Prefill immediately (question text/cached suggestion) and attach to a background task as needed; show a lightweight generating state, allow launching with current/free-form terms while synthesis runs, support cancel/timeout/error handling, add a “Regenerate” action, and never block the browser handoff on a slow model.
- [ ] **Precompute and cache suggestions:** Optionally run a bulk background task after each question-generation round to synthesize/cache queries for that round’s questions. Persist cached suggestions on `Question` (or an associated record) with clear invalidation/refresh semantics (explicit refresh; avoid surprising auto-regeneration) and reuse cached values when opening Research.
- [ ] **Gating, fallback, and logging:** Add a lightweight “worth searching?” heuristic before spending synthesis work on obviously non-searchable prompts (with a user override). Research must always work when synthesis is unavailable/slow/fails. Record synthesis/handoff activity as `Lookup`/`Tool` (or appropriate) log entries with query/terms, timing, and errors.
- [ ] **Decision-model gate evaluation (optional spike):** Evaluate whether a fast/cheap classifier is worthwhile beyond the heuristic (criteria, metrics, candidate models/runtimes and per-target availability, latency/quality/failure behavior vs baseline). If beneficial, design integration (routing/lifecycle, prompt/contract and confidence/override, caching, attribution, fallback) so it never becomes a blocking dependency; if not, document the decision and keep the heuristic-only path. *(Combines the two decision-model bullets into one gated item.)*
