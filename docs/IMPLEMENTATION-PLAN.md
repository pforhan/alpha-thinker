### 4C. Question pool & planning quality 
- [ ] **Global question pool:** Implement global question-pool management (create/edit questions reusable across projects) and integrate it with hardcoded/seed questions and LLM-generated questions (clarify precedence, dedupe, and per-project vs global scope). Define how pooled/user-defined questions are phased when added (assigned to a real phase vs unassigned/`NoPhase`; see unassigned-phase task) so they don’t silently misattribute to an arbitrary phase.
- [ ] mostly complete: **Unassigned phase (`NoPhase`) & slotting (design/model):** Consider a `NoPhase`/unassigned sentinel `Phase` implementation for questions without a real planning phase (e.g. portable import, global/user-defined questions, or cases where phase context is unknown). Define its semantics and touch points: stable key/identity and ordering/display rules (never a next-phase suggestion, not a visited library phase unless explicitly represented), `Phase` resolution/fromKey behavior, and how it appears (or is excluded) in `Project` phase lookup/stats/timeline, export snapshot/traversal/summaries, and prompt/context. Prefer explicit unassigned attribution over falling back to `ScopeGoals`; provide a path/UX to slot unassigned questions into real phases rather than leaving them orphaned.
- [ ] **Phase-fit reassignment & slotting (exploration/design spike):** Evaluate using a lightweight/decision model (e.g. a small local model such as tev1:0.8b, if viable) to rehome generated questions to a better-fitting phase when they don’t match the current phase, and/or to suggest target phases for unassigned (`NoPhase`) questions (e.g. after import or from the global pool). Capture feasibility, hosting/runtime constraints, confidence/override behavior, and when reassignment runs; implement only if justified. Always allow manual slotting into a real (built-in or custom) phase and treat suggestions as assistive, not authoritative.
- [ ] **Evaluate and expand summarize support:** Revisit summarization intent, prompts, and API shape (current single engine-backed method `PlanningEngine.summarizePriorAnswers` / `KoogPlanningEngine` prompt is compaction-oriented: “condense… so a later round does not ask again”; tests in `engine/KoogPlanningEngineTest.kt` focus on question generation and this compaction behavior). Plan for **multiple summary kinds/intents over time** (not just one method/prompt): prompt/context compaction vs export/document summaries vs cached/user-facing phase summaries may need different methods or an explicit intent/mode, prompts, and output expectations/length/structure (e.g. compaction favors settled decisions/constraints; export may favor themes, ideas, and insights). Update `PlanningEngine`/`PhaseSummarization`/`ProjectExportSummarizer` APIs, implementations, and tests accordingly, and ensure compaction, export, the 4A.4 snapshot+pipeline, and the persisted phase-summary cache can request, resolve, and store the appropriate kind per intent without conflating them.
- [ ] **Background phase summary generation (design/optional):** Build on the persisted phase-summary cache (4A.4) to optionally generate and store summaries when leaving a phase; if the phase is revisited, clear and regenerate on exit (or mark stale) per cache invalidation rules. Define when generation runs, user visibility/progress, and prompt/context usage, letting export and compaction prefer cached summaries before on-demand generation. Align generated summary intent with “Evaluate and expand summarize support” (compaction vs themes/insights) so reuse is correct.

## Phase 4.1: Research query synthesis (follows 4B answer work)

Improves the Research handoff by synthesizing project-aware search terms while preserving the question-generation JSON-array contract.

- [ ] **Query-synthesis engine API:** Add a `PlanningEngine` method to suggest **multiple ranked/labelled alternative query sets** for a question from project context (title, synopsis, phase, question, relevant prior answers/drafts). Engines that cannot synthesize (no capable model/window, Offline, etc.) must degrade gracefully to a cheap heuristic or title/question-derived terms—never fail the handoff.
- [ ] **Research dialog UX:** Present suggested query options as clickable actions (launch in browser and/or populate the question’s reference URL) alongside a free-form search-terms field. The user can always edit terms and launch immediately without waiting for suggestions.
- [ ] **On-demand synthesis + responsive UI:** When the answer dialog opens, kick off query generation if nothing is cached. Prefill immediately (question text/cached suggestion) and attach to a background task as needed; show a lightweight generating state, allow launching with current/free-form terms while synthesis runs, support cancel/timeout/error handling, add a “Regenerate” action, and never block the browser handoff on a slow model.
- [ ] **Precompute and cache suggestions:** Optionally run a bulk background task after each question-generation round to synthesize/cache queries for that round’s questions. Persist cached suggestions on `Question` (or an associated record) with clear invalidation/refresh semantics (explicit refresh; avoid surprising auto-regeneration) and reuse cached values when opening Research.
- [ ] **Gating, fallback, and logging:** Add a lightweight “worth searching?” heuristic before spending synthesis work on obviously non-searchable prompts (with a user override). Research must always work when synthesis is unavailable/slow/fails. Record synthesis/handoff activity as `Lookup`/`Tool` (or appropriate) log entries with query/terms, timing, and errors.
- [ ] **Decision-model gate evaluation (optional spike):** Evaluate whether a fast/cheap classifier is worthwhile beyond the heuristic (criteria, metrics, candidate models/runtimes and per-target availability, latency/quality/failure behavior vs baseline). If beneficial, design integration (routing/lifecycle, prompt/contract and confidence/override, caching, attribution, fallback) so it never becomes a blocking dependency; if not, document the decision and keep the heuristic-only path. *(Combines the two decision-model bullets into one gated item.)*

## Phase 8: Release build hygiene
- [x] won't do: **Debug-build split: the dev tools should not ship in a release binary.** *(Deferred from Phase 3.6 group E, which fixed the dependency direction so this is a build change plus a file move rather than a rewrite.)* Gate it on a Gradle property — `devTools`, default **on** so today's builds are unchanged — wired as a `devMain` source set the property adds and a `noDevMain` one whose actuals are the tool-free production versions of the same seams. Move `SampleProjectGenerator`, `ProjectSimulator`, `SimulatorScreen`, `TestingSheet`, `DelayControl`, and the engine delay (`EngineDelayConfig`, `EngineInteraction`, `SlowDownPlanningEngine`, the `SettingsKey`, `SettingsRepository.engineDelay`) into `devMain`, and delete `AppComponent`'s accessors for the tools plus the `SlowDownPlanningEngine` decorator the production graph then builds without. **Done — won't do:** the tools are reachable from the shipped UI, so a split would hide code the product already exposes while adding `devMain`/`noDevMain` source sets and expect/actual seams for an app this size; the chosen line is recorded in `ENG-DESIGN.md`'s "Tools vs. Product Code".
  - **The two composition points are what make it work.** `ChromeSheet.Testing` (`ChromeSheetHost.kt:82`, label `:139`) and `AppRoute.Simulator` (`NavApp.kt:98-99`) become `@Composable` slots — the dev build supplies the tool, the release build supplies something inert, and the nav root calls the same effect either way. `AppRoute.Simulator` also has to keep participating in the back and FAB rules at `NavApp.kt:117`, which is where "inert route" gets decided rather than defaulted.
  - **The delay decorator decides how much this buys.** An `expect`/`actual` `PlanningEngine` in `AppComponent` returns the plain chain in `noDevMain` and the `SlowDownPlanningEngine`-wrapped chain in `devMain`. If the delay is dropped instead — `KoogPlanningBackend`'s real timeout already duplicates it — `EngineInteraction` stops being a product concern and this item shrinks to the generator and simulator.
  - **Where the state lands matters as much as the code.** `SettingsKey.SimulatedProjectId` and the three delay keys sit in the user's real settings table today; behind the property they are dev-only rows, so decide whether a release build stops reading them or merely never writes them.
  - **The tests follow the tools.** `SampleProjectGeneratorTest`, `ProjectSimulatorTest`, `OpenSimulatedProjectTest`, `SlowDownPlanningEngineTest`, `SettingsViewModelTest`'s tool cases, and the two `ProjectDetailViewModelTest` sites that wrap an engine in `SlowDownPlanningEngine` move to a `devTest` source set — so wire the property such that a bare `./gradlew :shared:allTests` still runs them.
  - Proof: `./gradlew :shared:allTests` green with the property on, plus `:androidApp:assembleDebug` and `:androidApp:assembleRelease -PdevTools=false` (desktop and wasm equivalents), with no generator or simulator symbol in the release artifact.
