## Phase 3.8: typed activity-log events

Still relevant and unstarted. Deferred from the Phase 3.6 vocabulary audit's `LogMarkers` item. Today the log's writers and its read model are held together only by the `LogMarkers` string protocol: `LogContext` renders marker prefixes into each row's `log` text and `ActivityRecord` re-parses it with `startsWith` predicates, `batchCountRegex`, and a `TaskKind` name round-trip, so the read model imports `tasks` and reads enum names back out of prose. `LogMarkers` is also used directly by `TaskRunner` (cancelled row), `ActivityLogScreen` (row styling), `AnnounceFailuresTest`, and log tests/fixtures. A typed event kind on the row lets the reader read structured data instead; the app is pre-release, so `ActivityDatabase`'s `fallbackToDestructiveMigration()` makes the schema change cheap (current DB is v4 and already carries the nullable `raw` payload column — preserve it).
- [ ] **Add the typed event kind.** Add an `event` column on `LogEntryEntity` and a matching enum on `LogEntry` (`Started`/`Succeeded`/`Failed`/`Cancelled`/`Prompt`/`Response`/`Note`), threaded through `LogDao`/mappers; keep `log` as the row's display text so the viewer and headlines are unchanged. Bump `ActivityDatabase` (v4 → v5, destructive fallback — losing an existing log is acceptable).
- [ ] **Set the kind from the writers, not the text.** `LogContext` (`started`/`closeSucceeded`/`closeFailed`/`closeCancelled`/`prompt`/`response`/`append`, plus `contextChecked`/`round`/`contextCompacted` notes) and `TaskRunner`'s interrupted-cancel row set the event and carry any structured payload needed by the reader (e.g. the task kind/name for `Started`), so nothing lifecycle-related has to be parsed back out of `log`.
- [ ] **Delete `LogMarkers` and rewrite the reader/UI.** `ActivityRecord`'s marker predicates/headline parsing become event comparisons, its `taskKind()` round-trip reads the payload, and `ActivityLogScreen`'s row styling branches on the event. Remove remaining direct `LogMarkers` uses (e.g. `AnnounceFailuresTest`) once the protocol is gone.
- [ ] **Decide the payloads that would finish the job.** `batchCountRegex` parses the response payload (`"2 questions, done=false"`) and the round note's `Action:`/`Phase:` lines (`ActionMoreQuestions`/`ActionAdvancePhase`) stay free text; type those payloads too so the regex and note parsing go, or keep them explicitly as prose. Coordinate with Phase 3.9 so research/lookup `Tool` rows land with a typed event/payload rather than reintroducing marker strings.
- [ ] **Update the log tests and fixtures.** `ActivityRecordTest`, `LogContextTest`, `RoomActivityLoggerTest`, `LogDaoTest`, and `AnnounceFailuresTest` currently build/assert against marker strings (or assume them) and must construct/assert the event kind/payload instead; keep coverage for headline derivation, row styling, and attribution (including `Tool`-source rows) intact.
- Note: the `SettingsKey` collapse — 11 string keys (`database/Storage.kt:10-22`) behind 9 hand-written `getSetting → guard → set` blocks (`SettingsRepository.kt:80-161`) whose "only apply while still default" race-guard is repeated 8× — is the other strong typed-row candidate, but it stays **deferred to Phase 4**: it is a real migration and buys nothing until there are more settings.

## Phase 3.9: Answer-time research

Replaces the earlier Koog agentic/tool-loop idea with user-initiated, answer-time research: question generation stays a single JSON-array reply, and lookup is an app-driven action that helps fill an answer draft rather than a tool the LLM calls. This avoids a prompt/contract change for small models, keeps the user in control of facts, and reuses `Question.draftText`, the summarization call shape, and the existing `LogCategory.Lookup` / `LogSource.Tool` vocabulary.

- [ ] **Remove the `Tools` capability.** Delete `EngineCapability.Tools` and the "Tools" pill/slot from the status chrome (`EngineStatus`/`EngineStatusCopy`, picker/status rendering, and any capability lists) so the header reports only Network and LLM. Research is a user-initiated app action, not a per-engine tool-calling capability; update `EngineKind.capabilities` comments/docs accordingly.
- [ ] **Answer-dialog research action (UI).** Add a "Research" button/link in the answer dialog that opens an interleaving dialog to review/edit the search terms (defaulting to the question text) and runs the lookup (search/cancel). Results are written into `draftText` with a `Source: <url>` line and are never auto-committed; the user can keep typing instead of researching, and reviews/edits and commits the draft as a normal answer. The `Source:` link opens in the external/system browser; no in-app webview.
- [ ] **Search, fetch, and extract.** Choose the search backend/provider and where any provider key/config lives (no `ToolRegistry`/MCP agent seam). Run the search and fetch, perform crude extraction (tag-strip/collapse whitespace) with a size cap, and produce capped text plus the source URL. Define per-target limits/feasibility (e.g. arbitrary-origin fetch constrained by wasm/CORS).
- [ ] **Summarize and fill the draft.** Run a single summarization pass over the extracted text ("answer the question in ~80 words or reply UNKNOWN", reusing the summarization call shape) and write the sourced result into `draftText`. When summarization is unavailable or fails (e.g. Offline/no capable engine, model error/timeout, or empty extraction), fall back to inserting the capped excerpt/snippet and the `Source:` link so the research action still yields a usable draft.
- [ ] **Configuration and graceful degradation.** Research is opt-in by user action (pressing Research), so no dedicated enable/disable setting is needed unless the chosen search provider requires configuration such as an API key. Degrade cleanly when unconfigured, offline, provider-unreachable, or unsupported on a target — surface the state and let the user answer manually; never guess or silently fall back.
- [ ] **Activity log entries.** Record each research action as `Lookup`-category / `Tool`-source rows carrying the query, source/result summary, timing, and errors, tied to the relevant activity/project. Coordinate with Phase 3.8 typed events so these rows land with an event kind/payload rather than a marker string, and confirm `ActivityRecord` attribution/headlines stay correct when `Tool` rows are present.
- [x] **Doc cleanup (PRD + ENG-DESIGN).** Updated PRD §4.3 and §5.5 and ENG-DESIGN "LLM Inference Layer" / schema notes to describe answer-time, user-initiated research (draft fill, sourced, opt-in by action), removed Koog tool-calling/MCP/webSearch+fetchPage as the lookup mechanism and the Tools-capability pill, and dropped the "LLM on/off toggle alongside" phrasing.
- [ ] **Model-initiated uncertainty (follow-on, optional).** A generation prompt branch that can respond "insufficient" / request clarification (Phase 5 item) composes with this: the user can then research or answer. Keep any `NEED:`/uncertainty side-channel additive and out of the JSON array contract so small-model parsing stays unchanged.
