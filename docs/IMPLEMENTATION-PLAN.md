## Phase 4: Advanced Features & Export

**Focus:** (1) Export, (2) Answer work. Other items are follow-ons/backlog within the phase.

### 4A. Export (primary)

#### 4A.1 Export model & rendering
- [x] **Export configuration model:** Define export options and an export artifact/record model (e.g. project id, created timestamp, filename, format, config snapshot, storage location/ref or status). Initial options should cover at least: output name (default derived in UI from project title), include/exclude ignored questions, unanswered items, drafts, answer revision history, and optional LLM-generated summaries/sections; keep the model extensible. — `model/Export.kt` adds `ExportConfig` (incl. `outputName`), `ExportFormat`, `ExportStatus`, and `ExportArtifact` (config snapshot + storage ref/status/error).
- [ ] **Phase-structured Markdown renderer:** Generate a phase-grouped Markdown document (e.g. `## Scope & Goals`, `## Execution Plan`) with an opening "phase trail" summary (phases traversed, question counts, completion %). Rounds are internal metadata and do not appear in the export. Apply export options consistently (filtering/section inclusion).
- [ ] **Reconcile export with the transcript renderer:** Share the transcript’s *state semantics* and phase grouping (`PhaseTranscript`) with the export instead of maintaining a divergent format (`PlanningContext.kt` notes this intent, but `ProjectRepository.exportProject` currently predates phases, ignores rounds/`phaseForQuestion`, mishandles drafts/ignored questions, and emits malformed tables). Replace the current flat renderer and its single test as part of this work; export remains a detailed human document while the transcript remains the token-optimized prompt block.
- [ ] **Optional summarization in export:** Decide and implement whether/how export reuses existing summarization/context-building logic for overview or per-phase summaries when requested by config. Run as async work with a clear fallback when no capable engine is available so export still succeeds without summaries.

#### 4A.2 Generation, storage, and sharing
- [ ] **Export generation service:** Add an app-level export/use-case flow that builds the document from project data, reports progress/state, integrates with task/activity logging as appropriate, and handles failures/cancellation without corrupting saved artifacts.
- [ ] **Local persistence strategy:** Decide where generated exports live (filesystem, DB table/blob, or metadata table + file) using a KMP-friendly approach. Implement saving, naming/collision handling, and retrieval of export records per project; define retention/overwrite/regenerate behavior.
- [ ] **Per-platform save/share (expect/actual):** Implement platform-specific save and share/open flows (e.g. Android share/save intent, desktop save dialog or open containing folder, web download) behind a common interface, with graceful degradation where a capability is unavailable.

#### 4A.3 UI entry points & management
- [ ] **Project list export action:** Change project list swipe actions so **swipe right exports** (instead of delete). Redesign the delete affordance accordingly (e.g. swipe left and/or an explicit delete action/button with confirmation) and update swipe labels/icons/behavior and related tests to match.
- [ ] **Additional export entry points:** Add an export action in `ProjectDetailScreen` and, where layout allows, an export button/action on project cards. Reuse the same export flow and configuration UI from all entry points.
- [ ] **Export configuration UI:** Add a dialog/sheet opened before generation to configure export options (ignored/unanswered/drafts, revisions, summaries, etc.), show destination/filename context as relevant, and confirm/cancel generation.
- [ ] **Export library/management UI:** Provide a UI to view saved exports for a project (and/or globally, as appropriate) with actions to open/share/download, delete, and regenerate with the same or edited options. Surface generation progress and errors clearly.

## Phase 4.1: Research query synthesis (follows 4B answer work)

Improves the Research handoff by synthesizing project-aware search terms while preserving the question-generation JSON-array contract.

- [ ] **Query-synthesis engine API:** Add a `PlanningEngine` method to suggest **multiple ranked/labelled alternative query sets** for a question from project context (title, synopsis, phase, question, relevant prior answers/drafts). Engines that cannot synthesize (no capable model/window, Offline, etc.) must degrade gracefully to a cheap heuristic or title/question-derived terms—never fail the handoff.
- [ ] **Research dialog UX:** Present suggested query options as clickable actions (launch in browser and/or populate the question’s reference URL) alongside a free-form search-terms field. The user can always edit terms and launch immediately without waiting for suggestions.
- [ ] **On-demand synthesis + responsive UI:** When the answer dialog opens, kick off query generation if nothing is cached. Prefill immediately (question text/cached suggestion) and attach to a background task as needed; show a lightweight generating state, allow launching with current/free-form terms while synthesis runs, support cancel/timeout/error handling, add a “Regenerate” action, and never block the browser handoff on a slow model.
- [ ] **Precompute and cache suggestions:** Optionally run a bulk background task after each question-generation round to synthesize/cache queries for that round’s questions. Persist cached suggestions on `Question` (or an associated record) with clear invalidation/refresh semantics (explicit refresh; avoid surprising auto-regeneration) and reuse cached values when opening Research.
- [ ] **Gating, fallback, and logging:** Add a lightweight “worth searching?” heuristic before spending synthesis work on obviously non-searchable prompts (with a user override). Research must always work when synthesis is unavailable/slow/fails. Record synthesis/handoff activity as `Lookup`/`Tool` (or appropriate) log entries with query/terms, timing, and errors.
- [ ] **Decision-model gate evaluation (optional spike):** Evaluate whether a fast/cheap classifier is worthwhile beyond the heuristic (criteria, metrics, candidate models/runtimes and per-target availability, latency/quality/failure behavior vs baseline). If beneficial, design integration (routing/lifecycle, prompt/contract and confidence/override, caching, attribution, fallback) so it never becomes a blocking dependency; if not, document the decision and keep the heuristic-only path. *(Combines the two decision-model bullets into one gated item.)*
