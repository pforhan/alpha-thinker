## Phase 3.8: typed activity-log events

Deferred from the Phase 3.6 vocabulary audit's `LogMarkers` item. Today the log's writers and its read model are held together only by the `LogMarkers` string protocol: `LogContext` renders a marker prefix into each row's `log` text and `ActivityRecord` re-parses it with five `startsWith` predicates, a `batchCountRegex`, and a `TaskKind` name round-trip, so the read model imports `tasks` and reads enum names back out of prose. A typed event kind on the row lets the reader read structured data instead; the app is pre-release, so `ActivityDatabase`'s `fallbackToDestructiveMigration()` makes the additive column free.
- [ ] **Add the typed event kind.** An `event` column on `LogEntryEntity` (`Started`/`Succeeded`/`Failed`/`Cancelled`/`Prompt`/`Response`/`Note`) plus its enum on `LogEntry`; keep `log` as the row's display text so the viewer and headlines are unchanged; bump `ActivityDatabase` (destructive fallback — losing an existing log is acceptable).
- [ ] **Set the kind from the writers, not the text.** `LogContext.started`/`closeSucceeded`/`closeFailed`/`closeCancelled`/`prompt`/`response`/`append` set the event and carry the structured payload (the task kind name for `started`), so nothing has to be parsed back out.
- [ ] **Delete `LogMarkers` and rewrite the reader.** `ActivityRecord`'s five predicates become event comparisons, its `taskKind()` round-trip reads the payload, and `ActivityLogScreen`'s row styling branches on the event.
- [ ] **Decide the payloads that would finish the job.** `batchCountRegex` parses the response payload (`"2 questions, done=false"`) and the round note's `Action:`/`Phase:` lines stay free text; type those payloads too so the regex and the note parsing go, or keep them explicitly as prose.
- [ ] **Update the log tests and fixtures.** `ActivityRecordTest` (~30 marker-string rows) and `RoomActivityLoggerTest`/`LogDaoTest` build rows from `log` strings and must construct the event kind instead.
- Note: the `SettingsKey` collapse — 11 string keys (`database/Storage.kt:10-22`) behind 9 hand-written `getSetting → guard → set` blocks (`SettingsRepository.kt:80-161`) whose "only apply while still default" race-guard is repeated 8× — is the other strong typed-row candidate, but it stays **deferred to Phase 4**: it is a real migration and buys nothing until there are more settings.
